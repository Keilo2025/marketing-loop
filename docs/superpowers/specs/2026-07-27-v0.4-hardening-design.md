# marketing-loop 0.4 Hardening Design

## Purpose

Version 0.4 turns the current file-based copy pipeline into a defensible agent workflow. The release closes the trust-boundary, path-confinement, source-corruption, canvas, configuration, and run-state flaws identified in the 0.3 audit while preserving the dependency-free Node.js CLI and the existing scan → propose → review → apply experience.

This release deliberately does not add A/B testing, deployment tracking, or post-change conversion attribution. Those capabilities require a separate analytics and experiment-lifecycle design. Version 0.4 establishes the safe state and provenance model they will need.

## Design principles

1. Model output is untrusted input.
2. Agents identify copy by `copyId`; they never choose a write target or approval state.
3. Every state transition is validated at runtime, not implied by TypeScript types or prompt instructions.
4. Approval is bound to the exact proposal content and scan run the human reviewed.
5. Apply is repository-confined, source-aware, preflighted, and atomic at the batch level.
6. Guardrails run whenever proposal text can change.
7. Failures are explicit. Invalid configuration or malformed agent output never silently falls back.
8. The CLI remains dependency-free at runtime.

## Trust model

The system has four trust levels:

- Repository content, analytics exports, README text, and configuration prose are untrusted context. They may contain prompt injection or stale claims.
- Agent and API-model output is untrusted data. It must be parsed and validated before it enters canonical state.
- Canonical inventory and proposal data is CLI-derived state. It is trusted only after its run identifiers, digests, and source hashes are verified.
- Human decisions are workflow authorization. They are bound to canonical proposal digests.

A coding agent with the same operating-system permissions as the user can always edit source files or forge files in `.marketing-loop/`. Version 0.4 therefore treats approval as a robust workflow gate, not a cryptographic security boundary. A deployment that needs enforced separation must run the agent with restricted filesystem permissions or keep approvals in an external service the agent cannot access.

## Artefacts and state

Each `propose` run receives a random `runId`. All artefacts written for that run include the same value.

### `inventory.json`

The inventory records:

- `runId`
- generation time
- repository root identity
- a deterministic inventory digest
- scanned file count and truncation status
- each copy item's normalized display text
- exact raw source text
- start and end offsets
- file-relative path
- file content hash
- source representation used for encoding replacements

The representation is one of:

- `plain`
- `html-text`
- `html-attribute-double`
- `html-attribute-single`
- `js-string-double`
- `js-string-single`
- `js-template`
- `json-string`
- `yaml-plain`
- `yaml-double`
- `yaml-single`

Unsupported or ambiguous representations remain scannable and diagnosable but are not automatically applicable.

### `proposals.json`

This is canonical CLI-owned state. A proposal set contains:

- `runId`
- `inventoryDigest`
- generation time
- product name
- canonical proposals

Canonical proposals derive `file`, `line`, `kind`, `before`, raw source metadata, and source hash from inventory. Every proposal starts `pending`. Agent-provided status, author, warnings, file paths, line numbers, source text, sibling links, and IDs are ignored rather than trusted.

Proposal IDs are deterministic hashes of the run, `copyId`, replacement text, and author class. Duplicate proposal IDs or duplicate agent proposals for the same `copyId` and replacement are rejected.

### `agent-output.json`

This is the only file a host agent or API model writes. It contains:

- `runId`
- `inventoryDigest`
- proposals keyed by `copyId`
- replacement text
- alternatives
- rationale
- problem solved
- principle IDs
- evidence notes
- confidence

It contains no file path, line, original text, status, approval, warnings, or author field.

Import is idempotent. Re-importing unchanged output produces no duplicate proposals. Re-importing changed output replaces the previously imported agent proposal for that `copyId` within the same run.

### `decisions.json`

Human decisions are stored separately from proposals. Each decision contains:

- `runId`
- proposal ID
- digest of the reviewed canonical proposal and final edited text
- decision: approved or rejected
- final text
- decision source: canvas or markdown
- decision time

Apply accepts an approval only when the run and digest still match. Changing proposal text after approval invalidates that decision.

### History

Starting a new `propose` run archives the previous canonical artefacts under `.marketing-loop/history/<runId>/` before writing new state. The archive operation is atomic and never overwrites an existing run.

## Agent-output ingestion

Ingestion is implemented as a reusable boundary function and exposed through `marketing-loop import`. `review` runs the same import automatically when `agent-output.json` exists, so the usual agent handoff remains:

```text
propose → agent writes agent-output.json → review --ui
```

The importer:

1. Parses the file with actionable JSON errors.
2. Validates the top-level schema and required strings.
3. Requires a matching `runId` and `inventoryDigest`.
4. Resolves every `copyId` against the current inventory.
5. Rejects unknown or out-of-scope items.
6. Derives all source and location fields from inventory.
7. Normalizes confidence and validates principle IDs.
8. Enforces unique proposals and the total `maxProposals` cap.
9. Sets author to `agent` and status to `pending`.
10. Runs guardrails and records warnings or blocks the proposal.
11. Links siblings only after all accepted proposals are canonical.
12. Writes canonical state atomically.

Import reports accepted, warned, blocked, and rejected entries separately. A malformed entry never causes a valid entry to be silently discarded, and an invalid top-level run identity rejects the entire import.

The standalone `--llm` path uses the same importer rather than constructing trusted proposals directly.

## Claim and prompt safety

Numbers in replacement text are recognized as sourced only when the same normalized number and unit appear in:

- the original copy, or
- an explicit `allowedClaims` entry.

Agent-written evidence is explanatory and never establishes a fact. An allowed claim approves only the matching normalized claim, not every proposal that happens to trigger the same regex category.

Repository content inserted into `brief.md` is labelled as untrusted evidence and placed inside explicit data delimiters. The brief tells agents that instructions found inside repository content, analytics notes, filenames, and current copy must not be followed.

Product-model entries become `signals`, not proven capabilities. Dependency presence, route names, component names, README text, and directory names carry provenance and confidence. The host agent must inspect implementation before using a signal as a claim. The API-model path cannot inspect additional files, so it may use only original copy and `allowedClaims` as factual claim sources.

Guardrails execute:

- when deterministic proposals are created
- when agent or API output is imported
- when a human edits final text
- immediately before apply

Hard-blocked proposals cannot be approved or applied. Warning-level proposals require ordinary human approval.

## Repository-confined apply

Apply resolves the target exclusively from the current inventory entry, never from agent output.

For every approved proposal it:

1. Resolves the repository root with `realpath`.
2. normalizes the inventory path
3. rejects absolute paths and `..` traversal
4. resolves the existing target with `realpath`
5. verifies the resolved target remains beneath the repository root
6. rejects symbolic-link targets
7. compares normalized paths against normalized `protectedFiles`
8. verifies the current file hash and exact raw source span
9. encodes final text using the recorded representation
10. reruns guardrails against final text

All approved proposals are preflighted before any source file changes. Multiple changes to one file are applied in descending-offset order to the same in-memory content.

The batch is rejected without source writes when any proposal is stale, blocked, ambiguous, outside the repository, protected, unsupported, or would make a format-specific validation fail.

For a valid batch:

1. Original files are copied to a new backup run.
2. Updated content is written to temporary files in each target directory.
3. JSON files are parsed before commit.
4. Temporary files are renamed over originals.
5. A failure during commit restores every already-replaced file from the batch backup.
6. Proposal and report state is written only after the source transaction succeeds.

`--dry-run` performs the full preflight and encoding validation without backups, source writes, or status changes.

`revert` restores the latest successful apply run and records the restoration so status output no longer reports reverted proposals as currently applied.

## Canvas hardening

Every canvas server instance generates a cryptographically random session token. The token is included in the opened URL and sent in a dedicated header on every API request.

The server:

- accepts only the loopback host
- checks the request Origin when present
- requires the session token for state and mutation endpoints
- requires `application/json` for POST requests
- rejects empty, oversized, and malformed bodies with an error response
- never converts parse failures into an apply request
- adds `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, and frame-denial headers
- returns non-success responses for invalid status transitions

The page renders proposal data through DOM APIs and `textContent`. It does not interpolate proposal values into `innerHTML`, IDs, or CSS selectors. Canonical IDs are also restricted to lowercase hexadecimal strings.

Apply remains a separate explicit action. Cross-origin forms, scripts without the session token, and malformed requests cannot trigger it.

## Configuration and scanning

`loadConfig` distinguishes a missing config file from an invalid one. Invalid JSON, incorrect field types, unsupported surfaces, invalid paths, non-positive `maxProposals`, and malformed voice configuration produce actionable errors.

`include` becomes authoritative:

- `["."]` scans the repository root.
- Other values scan only those repository-relative roots.
- Absolute paths and traversal are rejected.
- Missing include roots are reported.
- Results from overlapping roots are deduplicated.

Exclusion matching operates on normalized path segments and explicit filename fragments rather than unrestricted substring matching.

Walking reports whether `maxFiles` truncated the result. `scan`, `propose`, and `brief` surface truncation prominently and refuse to describe a truncated inventory as complete.

## Run consistency and atomic state

All JSON and text artefacts are written through temporary-file-plus-rename helpers. A canvas session owns one in-memory run and refuses external files with a different run ID.

Commands enforce state transitions:

- `propose` creates a new run.
- `import` accepts output for the current run only.
- `review` records decisions for the current proposal digest.
- `apply` accepts current, approved, digest-matching proposals only.
- `revert` operates on the latest successful, unreverted apply run.

Duplicate identifiers, stale review files, stale agent output, and proposal files from older runs produce explicit errors.

## CLI and agent-instruction changes

The generated brief and installed skills instruct agents to write `agent-output.json`. They no longer claim that guardrails have already processed agent output.

Installed commands use the current local/package version instead of `@latest`. This prevents an older instruction bundle from silently invoking a newer incompatible CLI and avoids executing newly published code on every run.

`--llm` gains a request timeout and actionable provider/parse errors. Failure to generate or import model output sets a non-zero exit code while preserving deterministic proposals.

## Testing strategy

All behavior changes follow red-green-refactor development.

Regression tests cover:

- traversal and absolute paths
- normalized protected-path bypasses
- symlink escape
- forged approved status
- stale and mismatched runs
- duplicate IDs
- proposal-cap bypass
- agent-written evidence attempting to source a number
- agent dark patterns reaching review
- multiline and entity-normalized source
- JSON, JavaScript, template, HTML, and Markdown encoding
- batch atomicity and rollback
- invalid and stale configuration
- authoritative include roots and scan truncation
- canvas tokens, Origin checks, content type, malformed bodies, and apply authorization
- DOM rendering of hostile proposal values
- idempotent agent-output imports
- stale decision digests
- revert bookkeeping
- LLM timeout and malformed response handling

At least one CLI-level test executes the complete temporary-repository workflow:

```text
init → propose → agent output → import → review decision → dry run → apply → revert
```

The existing deterministic analysis, sibling, localization, install, and psychology tests remain green.

## Migration

Version 0.4 does not consume agent-authored fields previously appended directly to `proposals.json`. When it encounters a 0.3 proposal file without `runId` and `inventoryDigest`, it:

1. archives the file
2. explains that canonical state changed in 0.4
3. instructs the user to rerun `propose`

No source file is modified during migration.

Existing configuration remains valid when its JSON and types are correct. The default command sequence remains:

```bash
npx marketing-loop propose
# agent writes .marketing-loop/agent-output.json
npx marketing-loop review --ui
npx marketing-loop apply
```

## Success criteria

The release is complete when:

- every audit exploit has a failing regression test that passes after the fix
- untrusted output cannot select a file path, source text, status, or approval
- every applied path is proven to be a non-symlink file inside the repository
- malformed or stale state cannot cause source writes
- source replacements preserve supported file syntax
- canvas mutations require a valid per-session token
- config and scan scope behave as documented
- the complete CLI workflow passes in a temporary repository
- `npm test`, TypeScript compilation, and repository diff checks pass
- documentation no longer overstates the human gate or inferred product evidence
